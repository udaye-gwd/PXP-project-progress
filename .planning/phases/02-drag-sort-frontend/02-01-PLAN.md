**PART A: CRITICAL — Remove cdkDropListSortingDisabled from template**

In the component template, locate all three cdkDropList divs (TODO, IN_PROGRESS, DONE columns) and REMOVE the `cdkDropListSortingDisabled=[true]` attribute from each. This attribute BLOCKS intra-column reordering in CDK. Without removing it, CDK will not trigger drop events for within-column moves, and the enhanced handler logic will never execute.

**PART B: Replace current onTaskDrop handler (lines ~811-846) with enhanced version that:**

1. **Detect move type:**
   - If previousContainer === container (same column): intra-column move — calculate new position
   - If previousContainer !== container: cross-column move — use existing updateStatus logic (position set by backend to end of column per D-07)

2. **Intra-column position calculation (per D-03 to D-05 decisions):**
   - Extract tasks in the column after drop: `const columnTasks = this.tasks().filter(t => t.status === newStatus)`
   - Find tasks immediately before and after the dropped task using currentIndex
   - Calculate new position as middle of gap:
     ```typescript
     const tasksBefore = columnTasks.slice(0, currentIndex);
     const tasksAfter = columnTasks.slice(currentIndex + 1);
     const posBefore = tasksBefore.length > 0 ? tasksBefore[tasksBefore.length - 1].position : -500;
     const posAfter = tasksAfter.length > 0 ? tasksAfter[0].position : (posBefore + 1500);
     const newPosition = Math.floor((posBefore + posAfter) / 2);
     ```

3. **Optimistic update (per D-01):**
   - Immediately update this.tasks signal with new position and reordered array
   - Add task.id to recentlyDroppedIds to suppress animation
   - Update local array order: `tasks.sort((a, b) => a.position - b.position)`

4. **Show disabled state (per D-02):**
   - During API call, mark card with visual disabled state (opacity-50, pointer-events-none, or similar class binding based on `currentlyUpdatingTaskIds` signal)
   - Add a `currentlyUpdatingTaskIds = signal<Set<number>>(new Set())` signal if not exists

5. **Error recovery (per D-09, D-10):**
   - On API error:
     - Revert task position in local signal to pre-drop value
     - Revert task status if it was a cross-column move
     - Call `this.loadTasks()` ONLY on fatal errors (404, 403); on temporary errors (5xx, network), just show toast and revert
     - Show error toast: "Failed to reorder task"
   - Do NOT show reload UI or trigger full page reload

6. **After successful update:**
   - Replace optimistically updated task with server response (for any fields backend may have changed)
   - Remove task.id from currentlyUpdatingTaskIds
   - Clear recentlyDroppedIds after animation settles (existing pattern)

Key implementation notes:
- Use this.tasks.update() for signal mutations
- Cross-column moves still call updateStatus (D-07 applies — backend sets position to end of target column)
- Intra-column moves call updatePosition with calculated position and current status
- Gap-based calculation assumes backend has already assigned positions via Phase 1
- Revert logic must preserve original task state — store backup before optimistic update

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Frontend → Backend | Untrusted position value (user can send any integer) |
| Backend → Database | Position value must be validated (integer range, not negative for valid reorders) |
| User A → User B | Cross-user move of tasks (authorization must be checked at backend) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | onTaskDrop position calculation | mitigate | Frontend calculates position, but backend PATCH /api/tasks/{id}/position validates: (1) user is member of project, (2) position is integer, (3) position is within reasonable range (0 to max int). No business logic depends on position being trusted client input. |
| T-02-02 | Elevation | Task ownership in cross-column move | accept | Authorization check is at backend (requireMember). Frontend signal update is optimistic; server response is authoritative. If user tries to move task they don't have permission for, backend rejects and frontend reverts. |
| T-02-03 | Denial | Rapid reorder spam | mitigate | No rate limiting added at frontend (backend already has Bucket4j 60 req/min per IP). Frontend can add debounce if needed in future. Current phase: mitigate by showing disabled state during in-flight request (prevents double-drops). |
| T-02-04 | Information | Position leakage | accept | Position values are visible in API response and DOM — no PII, only task order. No confidentiality risk. |

</threat_model>
